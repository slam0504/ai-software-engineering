# 開發契約流程：盤點、有效條件、基線與證據

## 0. 目的與適用範圍

- **目的**：讓一張票在三件事上有可以檢查的依據。
  1. 動手設計之前，知道會影響哪些既有的責任。
  2. 知道目前哪些要求有效，以及這些要求的來源與採納關係。
  3. 提供比較改動前後與判斷原因的依據；依據不足時，明列為未確認。基線能協助歸因，不保證每次都能查明原因。
- **適用範圍**：先限定在本專案試用。這不是全域的協作規範，也不是工具。
- **與既有決策的關係**：
  - 本文件不回溯改變任何已經做出的決策。
  - B3b 的 CI-1a 仍然依照當時的決策停在 T0，不因本文件的基線規則而放寬。
- **與其他文件的關係**：
  - 回報的格式見 [`mailroom-templates.md`](mailroom-templates.md)。
  - 外部做法的來源與限制見 [`../architecture/external-references.md`](../architecture/external-references.md)。

## 1. 一份邏輯上的工作紀錄，分成兩個部分

每張票維護一份工作紀錄。它在邏輯上是一份，但分成兩個部分，各自有不同的變動規則。

| 部分 | 內容 | 變動規則 |
|---|---|---|
| 核准版本 | 責任盤點與處置（A）、有效條件（B）、驗證計畫（C） | 內容固定。要修改就出新版本，並重新核對、取得必要的授權。 |
| 執行紀錄 | 基線的實際結果、各條件的證據、過程中發現的遺漏（D） | 只追加。追加證據**不需要**重新授權，也不改變核准版本。 |

- 兩個部分共用同一套編號。執行紀錄只引用編號，不重抄條件的內容。
- **核准版本的識別方式**：用保存該版本的 commit，或把它的 SHA256 記在外部的交付紀錄裡。**不把檔案自己的雜湊寫回檔案內**。
- 執行紀錄的開頭要寫明它引用的是哪一個核准版本。
- 範本在 §6。

## 2. 區塊 A：責任盤點

### 2.1 盤點什麼

盤點的對象是**受這次改動影響的責任**，不是把整個系統列一遍。對每一個會被取代、修改或移除的元件，至少看下面七個面向：

| 面向 | 例子 |
|---|---|
| 輸入 | 參數、環境變數、設定檔、讀取的檔案 |
| 輸出 | 回傳值、寫出的檔案、紀錄的欄位 |
| 副作用 | 建立的程序、送出的 signal、對外的呼叫 |
| 生命週期 | 啟動、停止、清理、資源由誰持有 |
| 失敗處理 | 逾時、錯誤如何分類、哪些情況要停下 |
| 相容性 | 呼叫端、測試、fixture、其他票依賴的行為 |
| 隱含預設 | 沒有明寫、由函式庫或平台預設值決定的行為 |

- 每一項都要附來源：檔案與行號，或文件的段落與版本。
- 每一項另外標明**認知狀態**：已確認，或未知。查不清楚的項目標為未知，並寫出還缺什麼資料；不要用推測補上。

### 2.2 設計要逐項標示處置

設計對盤點的每一項，標出四種處置之一。處置和認知狀態是兩個不同的欄位：一個項目可以是「未知」，同時處置是「待裁決」或「保留」。

| 處置 | 意義 |
|---|---|
| 保留 | 行為不變。寫出它在新設計中由哪個部分負責。 |
| 替換 | 改用新的做法。寫出新做法，以及和原本行為的差異。 |
| 移除 | 不再提供。寫出理由，以及誰會受影響。 |
| 待裁決 | 需要 owner 決定。在裁決之前，不得當成已經決定來設計。 |

審查時看的是每一項的處置是否合理，不是只看編號有沒有出現。

### 2.3 依風險決定審查的深度

風險看的是**語意或責任邊界有沒有實質改動**，不是看檔案的類型，也不是看文件是否已凍結。

| 情況 | 做法 |
|---|---|
| 高風險：取代或移除負責程序管理、生命週期、持久化、授權或安全邊界的元件；或是實質改變已凍結契約的語意 | 盤點**先單獨審查**，通過之後才進入設計定案 |
| 一般改動 | 盤點併入設計文件，一起審查 |
| 小改動 | 不需要獨立的盤點；在交付信裡說明影響範圍即可 |

- 修正已凍結文件裡的錯字，不會因為文件已凍結就變成高風險。
- 純文件的改動，如果改到權限或驗收契約，不能自動走小改動的流程。
- 盤點審查之前，可以做必要的候選方案分析，以及已經獲得授權的調查；這些不算提前開始設計定案。
- 風險的判斷寫在工作紀錄的開頭，審查方可以提出異議。不是每張票都要多一道關卡。

### 2.4 盤點解決不了的問題

盤點能減少「漏掉既有責任」這一類的反覆，解決不了真正的設計問題。以 B3b 的 proposal-014 為例：

- **盤點可以提早發現的**：工作目錄的設定、檔案描述符的處理、各角色之間的差異。
- **盤點發現不了、屬於設計本身的**：回收之後的身分保證、spawn 的期限、無法分辨的退出原因。

所以盤點通過，不代表設計會一次通過。設計問題仍然要靠設計審查和有界的驗證來處理。

### 2.5 新機制與既有做法

- 提出新機制之前，先找有沒有成熟的做法可以用，並在設計中寫出找過什麼。
- 找不到先例時，可以提出新機制，但要寫出它依賴的假設，並安排有界的驗證，例如限定範圍與時間的 spike。
- 「必須有先例」不是硬性規定。

## 3. 區塊 B：有效條件

### 3.1 這份清單是什麼

有效條件清單是**核准契約的可追溯整併版本**。它不產生新的要求，只是把散在各處、已被採納的要求整理在一起，並保留每一條的出處。

- **有效驗收集合只包含已核准、而且沒有被取代的條件。**
- 還沒有核准的候選項目（提議、整理者的推論），以及已經被取代的歷史項目，都要保留，但分開列出，不混進有效集合。

每一條至少有下面幾個欄位：

| 欄位 | 說明 |
|---|---|
| 穩定的 ID | 跨版本不變。條件被取代之後，ID 不重複使用。 |
| 要求 | 引用原文，或忠實摘述並附原文位置。 |
| 來源版本 | 檔案、段落，以及固定版本（commit 或 SHA256）。 |
| 驗證方式 | 靜態檢查，或需要實測；需要實測時寫出契約要求的方式。 |
| 取代關係 | 取代了哪一條，或被哪一條取代，以及依據的指示。 |

### 3.2 指示何時生效，以及怎麼保存

**生效不取決於歸檔。**

- owner 明確的停止、撤銷或範圍變更，**立即適用**。保存原文與核對整併版本，是事後補上的追溯程序，不是生效的條件。
- owner 的指示明確表示取代前一項時，記錄取代關係即可，不需要停下來。
- 只有在指示的**適用範圍不清楚**，或和其他有效條件**真正矛盾**時，才停止受影響的工作並詢問。

**保存時要記錄四件事**：發話者、時間、原文、採納關係。

- 發話者要照實記錄。審查方的回覆經 owner 轉達時，發話者是審查方，不能標成 owner 親自說出的原話。
- owner 是否採納、採納的依據，另外記錄。

### 3.3 區分三種來源性質

| 性質 | 意義 | 能不能進入有效驗收集合 |
|---|---|---|
| 明示核准 | owner 明確核准或採納的內容，有可以引用的原文與採納依據 | 可以 |
| 提議 | 實作方或審查方提出、還沒有被採納的內容 | 不可以；列為候選 |
| 整理者的推論 | 整理清單的人從上下文推出來的內容 | 不可以；列為候選 |

### 3.4 整併時的衝突

- 兩個來源互相矛盾，而且沒有明確的取代關係時，**明列為衝突並送裁決**。不得預設「比較新的文字自動覆蓋舊的」。
- 裁決的結果寫進取代關係，並引用裁決的來源。

### 3.5 雜湊與授權是兩件事

- 雜湊只能固定內容，不能證明內容已經獲得授權。
- 整併清單出了新版本之後，要先由審查方核對它和來源一致，之後的交付與審查才引用新版本。
- 這項核對只決定「這份整併清單能不能被引用」，**不影響 owner 指示本身的效力**（見 §3.2）。

## 4. 區塊 C：驗證計畫與基線

### 4.1 基線規則

> 實作前，應建立與本次變更相關、版本和環境已記錄的基線；明列預期通過、預期失敗及未確認項目，並事先決定比較方法與停止條件。

- 基線的要求是「改動前的狀態可以辨識、可以比較」，**不是一律要求全部通過**。
- 依票的性質選擇基線：

| 票的性質 | 基線可以是 |
|---|---|
| 缺陷修復 | 一個可以重現的失敗 |
| 新功能 | 既有的行為，加上負向案例 |
| 文件變更 | 文件與連結的檢查 |
| 需要穩定全套測試的工作 | 把「全套測試穩定」明列為該票的開工條件 |

- 基線裡每個項目標成三種之一：預期通過、預期失敗、未確認。
- 標為「未確認」的項目，**在取得新的證據之前**，不得被解讀成通過，也不得被解讀成與本次改動無關。之後可以依新的證據更新判定，但要保留它原本是未知的紀錄。
- 比較方法和停止條件屬於核准版本，要在實作**之前**寫下來，不在看到結果之後才決定。

### 4.2 證據

- 基線的實際結果和各條件的證據，寫在執行紀錄（D），不寫回核准版本。
- 證據的取得方式、`pass` 的適用條件、整體 ACCEPT 的成立條件，都依 [`mailroom-templates.md`](mailroom-templates.md) §0。

## 5. 開工條件與停止條件

### 5.1 開工條件

- **盤點**：依 §2.3 的風險等級，完成對應深度的審查。
- **有效條件**：這次工作依賴的條件，都在有效驗收集合裡。
- **基線**：已依 §4.1 建立，比較方法與停止條件已經寫下。
- **未決的項目只阻擋依賴它的工作。** 標為「待裁決」或「未知」的項目，不妨礙和它無關的部分先開始。

### 5.2 過程中發現新的責任或問題

- 新發現的項目，如果可以在既有的授權範圍內修正：更新盤點，記下它是在哪個階段發現的，然後繼續。
- 新發現的項目，如果涉及契約、權限、安全、相容性或範圍的變更：停下受影響的工作，送裁決。

### 5.3 停止條件

出現下面任何一種情況，就停止受影響的工作並回報，不自行裁決：

- owner 明確要求停止、撤銷或變更範圍（立即適用，見 §3.2）。
- 有效條件之間真正矛盾，或某個指示的適用範圍不清楚。
- §5.2 所列、需要裁決的新發現。
- 基線無法辨識或無法比較，或是比較方法事先沒有決定。
- 審查輪次**達到**該票約定的上限時，仍然有阻擋項。

## 6. 工作紀錄範本

### 6.1 核准版本

```markdown

- 風險等級與理由：<高風險／一般／小改動；依 §2.3>

## A. 責任盤點
| ID | 元件 | 面向 | 現況（附來源：檔案行號，或文件段落與版本） | 認知狀態（已確認／未知；未知時寫缺少的資料） | 處置（保留／替換／移除／待裁決） | 新設計中的對應 |
|---|---|---|---|---|---|---|

|---|---|---|---|---|---|---|

### B.2 候選（提議、整理者的推論；不是驗收依據）
| ID | 內容 | 性質 | 提出者 | 狀態（待裁決／已採納並移入 B.1／不採納） |

| ID | 原要求 | 被哪一條取代 | 依據 |
```

## 7. 試用與評估

- **試用範圍**：本專案兩到三張性質不同的票，由 owner 選定。不必為了湊齊類型而特別開一張高風險的工作。
- **每張票結束時記錄三件事**：
  1. **有沒有提早發現遺漏的契約**：盤點階段找到幾項；設計、實作、審查階段才找到幾項（資料來自 D.3）。
  2. **能不能直接辨認有效的要求**：審查方核對有效驗收集合時，需不需要回頭翻其他文件來拼湊。
  3. **能不能分辨改動造成的失敗與基線的問題**：出現失敗時，靠基線紀錄能不能歸類。
- 第 3 項的答案可以是「依現有證據仍然無法歸因」。不為了證明流程有效而強行分類。
- **評估**：試用結束後，由 owner 依這三項的紀錄決定保留、調整，或是否值得自動化。在那之前，本文件只是文件慣例，不做成工具。
