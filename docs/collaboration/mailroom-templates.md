# mailroom 交付信與審查信範本

- **用途**：實作方（claude-worker）和審查方（codex-reviewer）之間交付與審查時，使用的固定格式。
- **適用範圍**：先限定在本專案試用，暫時不升成全域的協作規範。
- **借用來源**：review-bridge（commit `50185a2`）的四項做法：逐條判定、證據包、未執行清單、finding 追蹤。可借用的部分與限制，見 [`../architecture/external-references.md`](../architecture/external-references.md) §3。
- **不變的原則**：審查方的獨立 probe、反例與 mutation 能力照舊保留；範本只規定回報的格式，不限制查證的方法。

## 0. 共用規則

### 0.1 驗收 ID 的權威

- 驗收條件的權威來源是**固定版本的核准契約**，例如 DECISION、已核准的規格或計畫段落，或 owner 的裁決原文。交付信不是權威來源。
- 交付方和審查方都要**各自**核對該契約完整的 active 條件集合，並寫出契約的檔案、固定版本，以及 active 條件的總數。
- 契約本身沒有編號時，可以使用臨時編號（AC1、AC2…），但每個編號都要附上原條款的位置或原文對照。不得藉由重新編號來合併、改寫或刪除要求。
- 交付信漏列的條件，審查方要補列，並記為 finding。

### 0.2 證據取得方式

每一項證據都要標上代號。代號說明的是**寫這封信的人如何取得這項證據**，不代表證據是否充分。

| 代號 | 意義 |
|---|---|
| R | 本信署名者自己執行：自行重跑，或自行寫 probe、反例、mutation。要附指令、rc 和 log 路徑。 |
| L | 讀取他人執行所留下的 log 或 artifact。要附檔案路徑、SHA256，以及**原執行者**。 |
| S | 只檢查原始碼或文件，沒有任何執行結果。要附檔案與行號，或文件段落。 |
| N | 沒有做。要說明原因。 |

- **代號以本信署名者為準**。subagent 執行、主審只讀 log 時，主審要標 L，並記錄原執行者是該 subagent。
- **R 不一定比 L 充分**。證據是否充分，要看它是否符合契約對該條件的驗證要求，不是看取得方式。

### 0.3 判定值與 `pass` 的適用條件

- 判定值只有三種：`pass`、`fail`、`cannot_verify`。
- `pass` 的條件，取決於契約對該條件的要求：
  - **文件或靜態結構的要求**，例如文字、欄位、檔案位置：可以由 S 支持。
  - **要求實測的條件**，例如行為、時序、測試結果：必須有符合契約的執行證據，也就是 R，或是可以追溯到實際執行的 L。只有 S 時不得判 `pass`，就算註明「沒有執行驗證」也不行。
- `cannot_verify` 不算通過。「沒有足夠證據提出 fail」也不算通過。
- 判 `cannot_verify` 時，寫出缺少哪些證據，以及缺少的原因。不必為了填表而虛構一項證據。

### 0.4 整體 ACCEPT 的成立條件

- 只要有任何一個必要條件是 `fail` 或 `cannot_verify`，或是還有尚未關閉的阻擋性 finding，就**不得**判整體 ACCEPT。
- 只完成局部審查時，要明列局部結論，並寫明「整體審查未完成」。局部結論不得寫成整體判定。
- 已經核准的例外，必須引用核准它的決策，附檔案與固定版本。審查方不得自行把違反要求的事項降級成觀察或殘餘風險。

### 0.5 finding 的等級與是否阻擋

- **等級**沿用 P1／P2，表示影響的大小。
- **是否阻擋**另外用 `blocking` 欄位（是／否）標示，依契約判定：違反契約、DECISION 或驗收條件的事項就是阻擋。
- P2 不會自動等於可以忽略；P2 也可能是阻擋項。

### 0.6 版本綁定

- 交付方和審查方都要寫出對象的固定版本：commit／tree，或 source manifest 的 SHA256，或文件的 SHA256。
- 審查方要說明自己怎麼核對這個版本，例如逐檔比對雜湊、tree 相同，或只比對了選取的檔案。只核對了一部分時，要寫出核對的範圍。

### 0.7 決策與結論分開

- 「核准決策」和「實作者的結論」是兩種東西，要分開引用。
- 核准決策引用時要帶固定版本。實作者的結論一律視為待核對的主張。

### 0.8 數字與紅燈

- 數字要當場數過再寫，並附上分母。
- 環境造成的失敗，不計為「紅在正題」。
- 紅燈要先分類，不用重跑把它吸收掉。

## 1. 交付信範本（實作方 → 審查方）

```markdown
# 交付：<票號> <標題>（第 <n> 輪）

## 1. 範圍與性質
- 本次交付的性質：<方案審查／實作審查／關票文件審查>
- 授權依據：<決策或計畫段落；附檔案與固定版本>
- 不在本次範圍：<明列>

## 2. 固定版本
- 對象：<commit／tree，或 source manifest 的 SHA256，或文件的 SHA256>
- 基準：<base commit 或前一版的 SHA256>
- 證據目錄：<路徑；不得放在揮發目錄>

## 3. 契約與驗收條件
- 契約來源：<檔案與固定版本>
- active 條件總數：<n>（我方已核對契約的完整集合）
| ID | 條件 | 原條款位置或原文對照 | 契約要求的驗證方式（靜態／實測） |
|---|---|---|---|

## 4. 變更（由工具取得，不是手寫）
- 取得方式：<git diff base...head／manifest 比對；附指令>
- 變更清單：<檔案與增刪行數>
- 開始前就存在、不屬於本次的變更：<有或無；有就列出>
- 我方宣稱、但上面的清單沒有涵蓋的項目：<有或無；有就列出並說明>

## 5. 我方對每個條件的主張（待核對）
| ID | 主張（done／not_done／blocked） | 證據與取得方式（R／L／S；L 要寫原執行者） |
|---|---|---|

## 6. 驗證結果
| 項目 | 指令 | rc | 結果（附分母） | 環境（load 等） | log 路徑 | 取得方式與執行者 |
|---|---|---|---|---|---|---|
- 沒有執行的項目與原因：<明列>
- 失敗與分類：<保留的紅燈、分類、有沒有重跑>

## 7. 揭露
- 偏離計畫或指示的地方：<明列>
- 已知限制與未驗證的項目：<明列>
- 執行者（subagent）的報告與主審核對不一致的地方：<有或無>

## 8. 需要 owner 裁決的事項（不請審查方代為決定）
- <明列；沒有就寫「無」>

## 9. 上一輪 finding 的處理
| finding ID | 處理（已修／不同意／延後） | 依據與取得方式 |
|---|---|---|

## 10. 建議的初始閱讀範圍
- <變更的檔案，加上直接呼叫者、使用者與測試>
- 這只是初始範圍；審查方可以沿著具體問題擴大。
```

## 2. 審查信範本（審查方 → 實作方／owner）

```markdown
# 審查：<票號> <標題>（第 <n> 輪）

## 1. 判定
- 整體：<ACCEPT／CHANGES_REQUIRED／NEEDS_REVISION／停止回報／整體審查未完成>
- 整體 ACCEPT 的條件是否成立：<所有必要條件都是 pass，而且沒有未關閉的阻擋性 finding；不成立就寫出是哪一項>
- 本次審查的性質與邊界：<例如「方案審查，不是實作授權」「授權，不是驗收通過」>
- 只完成局部審查時：<局部結論；整體未完成的部分>

## 2. 審查的版本
- 對象：<commit／tree／SHA256>
- 核對方式：<逐檔比對／tree 相同／只比對選取的檔案；寫出範圍>
- 沒有核對的部分：<明列>

## 3. 逐條判定
- 契約來源：<檔案與固定版本>
- active 條件總數：<n>（我方已自行核對契約的完整集合，不以交付信為準）
- 交付信漏列或改寫的條件：<有或無；有就列為 finding>
| ID | 判定（pass／fail／cannot_verify） | 證據與取得方式（R／L／S） | 缺少的證據與原因（判 cannot_verify 時填） |
|---|---|---|---|
- 每個 active 條件恰好一列。

## 4. Findings
| ID | 等級（P1／P2） | blocking（是／否） | 位置（程式行／契約段落／artifact） | 違反的條件或契約 | 主張 | 證據與取得方式 | 修正條件 |
|---|---|---|---|---|---|---|---|
- finding ID 跨輪次保持不變。
- 位置可以是程式行號、契約或方案的段落，或 artifact 的路徑。
- 新的 finding 不限於變更的檔案。
- 違反契約、DECISION 或驗收條件的事項，blocking 為「是」，不得列為觀察或殘餘風險；已核准的例外要引用決策。

## 5. 上一輪 findings 的狀態
| finding ID | 狀態（open／closed） | 關閉依據與取得方式，或仍未解決的原因 |
|---|---|---|
- 已關閉的也要列出，不得只是從回報中消失。

## 6. 本次實際做了什麼
- R（本信署名者自己執行）：<指令、probe／反例／mutation、rc、log 路徑>
- L（讀取他人的 log）：<檔案、SHA256、原執行者>
- S（只檢查原始碼或文件）：<檔案與行號、文件段落>

## 7. 本次沒有做的事（N）
- <沒有重跑的測試、沒有核對的檔案、沒有驗證的假設；附原因>

## 8. 停止與裁決
- 需要 owner 裁決的事項：<明列>
- 停止的原因（若有）：<需要 owner 決定／超出授權範圍／涉及發布動作／新的契約衝突>
- 對後續授權的建議：<可以或不可以進下一步，以及前提>

## 9. 審查的副作用
- 我方產生的檔案、程序與隔離複本：<位置；是否已清理或回收>
- 對交付物、candidate、方案的修改：<無；有就明列>
```

## 3. 與先前做法的差異

| 項目 | 先前做法 | 範本 |
|---|---|---|
| 驗收 ID | 視情況才逐條列出 | 以固定版本的契約為權威，雙方各自核對完整集合 |
| 證據取得方式 | 用文字說明，例如「本次未重跑…只核對…」 | 每一項都標 R／L／S／N，以署名者為準 |
| 逐條判定 | 視情況才寫 | 每個 active 條件恰好一列，另有 `cannot_verify` |
| 整體判定 | 由審查方敘述 | 明定整體 ACCEPT 的成立條件 |
| finding 追蹤 | 各輪各自敘述 | ID 固定；有等級和 blocking 兩欄；關閉要附依據 |
| 版本核對 | 寫出 SHA，核對範圍用文字說明 | 明寫核對方式與沒有核對的部分 |

## 4. 試用紀錄

- 首次試用：本範本所在的文件 PR（外部參考對照、本範本、backlog rev88）的交付與審查。
- 試用後要不要調整、是否擴大適用範圍，由 owner 決定。
